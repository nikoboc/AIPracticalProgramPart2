## このパートの位置づけ

講座の締めくくり。受講者が**自分のオリジナルのワークフロー**を作り始める前に、開発の基本的な流れ（フレームワーク）と注意点を学ぶ。後半は**わざとエラーが仕込まれたワークフロー**を使った、反復とトラブルシューティングの演習。

## 説明している内容

### AIワークフロー構築フレームワーク（4ステップ）

| # | ステップ | 内容 |
|---|---|---|
| 1 | **成功の定義（PRD作成）** | 何を作りたいか、どういう動きをするワークフローを作りたいか。**目的と成果物を明確化**する |
| 2 | **流用** | ゼロから全部考えて作るのではなく、**既存のリソース（AI生成・テンプレート・お手本）を活用**する |
| 3 | **反復** | テスト実行とテスト改善の繰り返し |
| 4 | **トラブルシューティング** | エラーが出たとき、どこがエラーか／どのノードが動いていないかという問題を見つけ、解決する |

> この4つを順番にしっかり丁寧に回していけば、**どんな人でも必ず自動化の仕組みを完成させられる。**

**このフレームワーク自体は現行でもそのまま有効。** 変わったのは、各ステップで使える道具が増えたこと。

### ステップ1：成功の定義（PRD作成）

- 最も重要。いわゆる**仕様書**にあたる。
- **何のために、どんな自動化を作りたいのか**を自分の中ではっきりさせること。
- 例：**毎朝のニュースを要約して Slack に通知する**
  - 必要なプロセスを頭の中で考える：ニュースサイトを見る → 記事を集める → 要約する → Slack に送る
  - 必要なツールを洗い出す：要約するための AI、Slack のノード
- こうしておくことで、**自分が今何を作っていて、どこを作っているのかが分かり、迷子にならずに進められる。**

> 【追記】現行では、**この「成功の定義」がそのまま AI Workflow Builder への入力になる。**「ちゃんと書けていれば AI が動くものを組んでくれる／曖昧だと的外れなものが出てくる」という形で、PRD の質がそのまま成果物に跳ね返る。**ステップ1の重要性はむしろ上がった。**

### ステップ2：流用（現行版）

- **自分でゼロから作らない。**
- 作りたいワークフローは、ほとんどの場合**すでに世界の誰かが似たようなものを作っている**。

現行では、流用の手段が3段構えになる。

| 手段 | 内容 |
|---|---|
| ① **AI Workflow Builder**（新） | ステップ1で書いた内容を自然言語で入力すると、**動くワークフローが生成される**。既存ワークフローの修正・デバッグにも使える |
| ② **テンプレート** | n8n のテンプレートには **12,428 件**（2026-09-21 時点）が公開され、日々増え続けている。使いたいツール（Slack、Google シート、Gmail など）ややりたいことで検索する |
| ③ **YouTube・ネット上のチュートリアル** | 引き続き有効 |

> 【AI Workflow Builder の使い方の勘どころ（公式の推奨）】
> **大きく複雑な自動化は、一発で作らせようとしない。** まず AI Workflow Builder でざっくりした「地図」を作り、**実行 → プロンプトで修正 → 再実行**を繰り返す。これは次のステップ3「反復」とまったく同じ考え方。

> ⚠️ 【流用時の注意（追記）】**テンプレートや解説記事には 1.x 時代のものが大量に残っている。**
> - 「Save ボタンを押す」「Active トグルをオンにする」という説明は、現行 UI には存在しない（自動保存＋ Publish）。
> - AI Agent ノードの **Agent type を選ぶ**という説明も、現行では選択肢自体がない。
> - 古いバージョンのノードが含まれるテンプレートは、インポートしても動かないことがある。

### ステップ3：反復

テストと改善を繰り返すプロセス。**非常に重要なポイント：**

> **一つ修正を加えたら、一度テストを実行する。**

- 例えば10箇所が赤くなっている状態で、10箇所全部を自分流に修正してから最後にテスト実行すると、またエラーが出たときに**10箇所のうちどこが原因だったのか分からなくなる**。
- **1つノードを追加したら1つ実行**。1つ1つ丁寧に追加していくことが、**結果的に一番の最速**でワークフローを完成させる方法。

> 【追記】現行では**自動保存されるので「保存し忘れて消える」心配はない**が、そのぶん「**どの状態まで動いていたか**」が分かりにくくなる面がある。**バージョン履歴**（②参照）で節目の状態に戻れることを伝えておくと、受講者は安心して試せる。
>
> 【発展】AI の出力の良し悪しは、実行するたびに変わる。n8n には **evaluations**（Evaluation Trigger / Evaluation ノード）という仕組みがあり、**あらかじめ用意したテストケースを流して結果を比べる**ことができる。「感覚で良くなった気がする」から「数字で良くなったと言える」に進みたい受講者向けの次の一歩として紹介する。

### ステップ4：トラブルシューティング（現行版）

- 反復の最中に**必ずと言っていいほどエラーに出会う**。
- エラーが起きたときに**原因を理解して解決策を実行する**プロセス。
- **開発経験が少ない人にとって、AI時代における「AIを使った反復とトラブルシューティング」の方法を学ぶことは、何よりも重要なスキル。**

現行では**2段構え**で教える。

#### 第1手段：n8n の中で解決する（新）

| 機能 | 使いどころ |
|---|---|
| **n8n Assistant** | チャットからワークフローの作成・編集・テスト・トラブルシューティングを依頼する |
| **Ask n8n AI** | n8n の使い方についての質問 |
| **AI Workflow Builder** | 自然言語でワークフローを修正・デバッグする |

→ **ワークフローを外部に持ち出さずに済む**ので、情報の取り扱いの面でも安全。まずこちらを試す。

#### 第2手段：外部の AI に相談する

解決しない場合は ChatGPT や Google AI Studio（Gemini）を使う。**AIに投げるプロンプトには以下の3点を必ず含める：**

| # | 含めるもの | 取り方 |
|---|---|---|
| 1 | **エラーメッセージ** | 画面下部のアウトプットのエラー部分を押すと、詳しいエラーが出る。コピーできる |
| 2 | **ワークフローの概要（JSONファイル）** | ワークフローをエクスポートした JSON を添付する |
| 3 | **依頼文** | 「このエラーを解決したいです。何がエラーになっていて、どのように解決すればいいか教えてください」 |

> ⚠️ **【追加の手順】JSON を外部に渡す前に、中身を確認する。**
> - **Credential に登録した認証情報は JSON に含まれない**（安全）。
> - しかし**ノードのパラメータに直書きした値は含まれる**：API キー、メールアドレス、社内の URL、顧客名など。
> - 心当たりがあれば、**該当部分をダミーの文字列に置き換えてから渡す。**
> - ⑦で API キーを Credential に登録してあれば、この問題はほぼ起きない。**「認証情報は Credential に入れる」という習慣が、ここで効いてくる**という形で振り返る。

## 演習：わざとエラーが出るワークフローの修正

### 演習用ワークフローの読み込み

1. 講師が指定する URL にアクセスし、**ワークフローのファイル（JSON）をダウンロード**する。
   > ⚠️ 元動画ではこの URL が明示されていない。**再収録時に配布先を確定させること。**
2. n8n のワークフローメニューから **「Import from File」** を選び、ダウンロードしたファイルを開く。
3. → ワークフローが表示される。
   - 構成：**RSS トリガー**で指定されたサイト（例：Yahoo!ニュース）から情報を抽出し、**Edit Fields（Set）ノード**につながっている、ごくシンプルなワークフロー。

> 【追記】現行の n8n には **n8n packages（`.n8np`）** という形式もある。ワークフロー単体ではなく、**フォルダやプロジェクトごと、依存するサブワークフローや Data table もまとめて**書き出し・取り込みできる。演習では従来どおり JSON で十分だが、受講者が業務で複数ワークフローを移送する場面では有用。

### 1回目のテスト実行

1. **Execute Workflow** でテスト実行する。
2. → **エラーが出る**。演習としては想定どおり。

### トラブルシューティング

上記「ステップ4」の手順で、まず n8n Assistant、それでも解決しなければ外部の AI に相談する。

### 修正の適用

- AI が原因を洗い出してくれる。
  - **原因：ノードの値に入っている「式」の文法ミス。**
  - 「あなたのワークフローを見ると、ここの値が次のようになっていて、正しい書き方はこうです」と提示され、**修正手順**が示される。
- 修正手順どおりに作業：
  1. n8n でエラーが出ているノードを開く。
  2. **値の欄の右にある `fx` をオン**にする（固定値 → 式 に切り替える）。
  3. 値を、AI が示した**正しい式に差し替える**。
- 修正したら**再度実行**。
- → **ワークフローは「成功」の表示になる。**

### しかし成功していない（重要な学び）

- 実行は成功と表示されたが、**アウトプットには何も表示されていない。**
- このワークフローは**ニュースサイトからタイトルを引っ張ってきて表示させる**ものなのに、結果が得られていない。
- **ステップ1「成功の定義」**に立ち返ると、このワークフローの成功の定義は**「抽出したニュースサイトのタイトルを表示する」**。
- **ワークフロー自体が成功していても、自分が欲しい結果が得られていなければ、それは失敗。**
- そのため、**ステップ3（反復）とステップ4（トラブルシューティング）を繰り返す必要がある。**

> この「緑になったのに欲しいものが出ていない」という体験が、この演習の核心。**現行仕様でも完全にそのまま有効。**

### 2回目以降の反復

1. 画面のスクリーンショットを撮る、またはワークフローを再度エクスポートして JSON にする。
2. 「ワークフロー自体は成功したけれどもタイトルが表示されません。どのように改善したらいいですか」と送る。
3. **自分の求めている結果が出るまで、AI と壁打ちして解決していく。**
4. 最終的に、抽出したニュースサイトのタイトルがアウトプットに表示されれば**演習完了**。

## 【新規追加】完成したら Publish する

動画にはないが、**現行の n8n では「作り終えた」だけでは本番では動かない**ため、締めの直前に必ず入れる。

1. テスト実行で欲しい結果が得られたことを確認する。
2. **Publish** ボタン（`Shift` + `P`）を押して公開する。
3. 公開して初めて、
   - スケジュールが設定した時刻に動く
   - Webhook・フォームが本番 URL で受け付ける
   - 連携アプリのイベントでワークフローが起動する
4. 公開後にキャンバスを編集しても、**再度 Publish するまで本番の動きは変わらない。** 安心して手を入れられる。
5. うまくいかなくなったら、**バージョン履歴から前のバージョンに戻せる／Unpublish で本番から外せる。**

> ②で教えた「編集はドラフト、本番は公開バージョン」がここで回収される。**この講座で最も大きい仕様変更なので、最後にもう一度確認する。**

## 演習からの学び（締めのメッセージ）

- AIとの対話において、**こちらの意図・目的を明確に伝えるプロンプトがいかに重要か**を体感してほしい。
- エラーが起きたとき、AIの回答は素晴らしいヒントになる。しかし同時に、**n8n の基本的なデータの流れを自分でも理解していくことが、トラブルシューティングを簡単にする重要な鍵**になる。
  - **前のノードから次のノードへデータが正しく渡されているか**
  - あるノードの**アウトプット**と、次のノードの**インプット**
  - **どのノードまで正しく動いているか**を確認する癖をつける。
- 今後は AI を使って、さらに一歩進んで **n8n で使える簡単なコード（JavaScript など）**にも取り組める。
- この講座では、**ノーコードプラットフォームにおけるデータフローの構造**を学んできた。
  - データが RSS フィードから取り込まれ、ノードで処理され、結果が出力される。
  - **コードの知識がなくても、こうした論理的な思考でワークフローを構築できる点が n8n の画期的な部分。**
- AI を活用しながらエラー対処と改善を反復することで、**論理構造への理解は思うよりずっと早く深まる。**
- **AI はあくまでヒントや選択肢を提供してくれる優秀なアシスタント。** AI が出した選択肢やヒントを**どう採用し、どう修正するのか、その最終的な判断は必ずあなた自身（人間）が行う必要がある。**
- 【追記】**これは n8n の中の AI 機能（AI Workflow Builder / n8n Assistant）にも同じく当てはまる。** 自然言語で組んでくれる時代になったからこそ、「**出てきたものが自分の成功の定義を満たしているか**」を判断できる人間が必要になる。フレームワークのステップ1が最重要である理由。
- この感覚を忘れずに、オリジナルのワークフロー構築にチャレンジしてほしい。
