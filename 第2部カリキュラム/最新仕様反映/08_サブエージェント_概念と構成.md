## このパートの位置づけ

AIエージェントのパフォーマンスを最大化するための強力なテクニック、**サブエージェント**を学ぶ。⑦で作った Tavily の HTTP Request を**リサーチ担当のサブエージェントに移し**、メインエージェントから呼び出す構成を作る。

## 説明している内容

### サブエージェントとは

- **メインエージェントの下に、それぞれの専門分野を担当するサブエージェントを配置する**という考え方。
- 例え：会社で優秀なマネージャーの下に、リサーチ担当の部下、メール作成担当の部下、データ分析担当の部下が配置されるイメージ。**AI同士のチームを組む／専門家を一人ずつ作る**感覚。

### なぜサブエージェントが必要か

一つのメインエージェントに「あれもこれも」と指示を詰め込むと：

- AIエージェント自体が**混乱しやすい**
- **出力が安定しない**／エラーばかり出る可能性が高くなる
- 安定した出力結果を目指すと**より複雑なシステムメッセージ**が必要になり、**コストがかさむ**

> 【補足】⑥で触れた MCP サーバー接続でツールを一気に増やせるようになった分、**この問題は動画当時より起きやすくなっている。** サブエージェントの重要性はむしろ上がっている。

### 【書き直し】サブエージェントの構成方法は3つ

動画では「①同一キャンバス／②別キャンバス」の2択で、②を推奨していた。現行の n8n では **同一キャンバス側に専用のノード（AI Agent Tool）が用意された**ため、3つの選択肢として整理し直す。

| 方法 | 実現手段 | 向いている場面 |
|---|---|---|
| ① **同一キャンバス + AI Agent Tool ノード**（新） | メインの AI Agent の Tool に **AI Agent Tool** を接続。そのサブエージェントにもモデル・ツール・システムメッセージを持たせる。入れ子にして多段も可能 | 役割分担はしたいが、**サブエージェント単体で再利用する予定がない**とき。データの受け渡しを意識せずに済み、**構成が最も速い** |
| ② **別キャンバス（別ワークフロー）+ Call n8n Workflow Tool** | サブエージェントを別ワークフローとして作り、メインから呼ぶ（動画の方法） | **複数のワークフローから同じサブエージェントを使い回したい**とき、**担当者を分けて保守したい**とき、**本番の公開バージョンを個別に管理したい**とき |
| ③ **Agent Builder のサブエージェント**（Preview） | n8n の「エージェント」機能で作ったエージェント同士を、公開済みエージェントとして委譲でつなぐ | ワークフローではなく**エージェントそのものを成果物として運用する**とき |

> **本講座の方針**：動画どおり **② 別キャンバス**をメインで教える。理由は下の「別キャンバスにするメリット」がそのまま生きているため。ただし、**① AI Agent Tool の存在は必ず紹介する。** 受講者が自作するとき、簡単な役割分担なら①のほうが早く、挫折しにくい。

### 別キャンバスにするメリット（動画の主張・現行でも有効）

- エージェントごとにキャンバスを完全に分けることで、**機能の追加・修正がそれぞれしやすくなる**。
- **どこで問題が起きたかを特定しやすい**＝**エラーハンドリングがしやすい**。
- 1つのワークフローに何もかもつなげると、どこでエラーが起きていてどこを修正すればいいかが分かりにくくなる。
- 【追記】現行ではさらに、**サブエージェントごとに独立した公開バージョンを持てる**というメリットが加わった。メインを直さずにサブだけ差し替える、といった運用ができる。

## 画面操作の手順

### 1. サブエージェント用のワークフローを新規作成

1. メインの `デモ` キャンバスはそのままにして、**Overview ページに戻る**。
2. **「Create Workflow」**から新規キャンバスを開く。
3. 名前を付ける（例：**サブエージェントサーチ**）。

### 2. トリガーの設定（他ワークフローから呼び出される側）

- サブエージェントは、メインエージェント（マネージャー）から**呼び出されて動く部下**である必要がある。

1. キャンバスでトリガーを検索し、**`Execute Sub-workflow Trigger`**（キャンバス上の表示は **When Executed by Another Workflow**）を追加する。
2. トリガーノードの設定で、**Input data mode** を **`Accept all data`** にする。
   > 動画で「Data Mode を All Data に」と言っているのがこれ。**現行のラベルは `Accept all data`。**
   - 他の選択肢：`Define using fields below`（受け取る項目を明示的に定義）、`Define using JSON example`（JSON の例から定義）
   - 【補足】受け取る項目を定義しておくと、メイン側の Call n8n Workflow Tool で **Refresh** を押すだけで入力欄が生成され、間違いが減る。**本格的に運用するなら定義する方が安全**だが、講座では動画どおり `Accept all data` で進めてよい。

### 3. AI Agent と Chat Model を追加

1. トリガーの**＋**から **AI Agent** を追加（メインと同じ）。
2. Chat Model も同じく **OpenRouter Chat Model** を追加（または④のルートA：Gateway credits）。
3. 認証情報のプルダウンを見ると、**④で登録した Credential がそのまま選べる**。
   - → **一度 Credential を登録すれば、全く別のワークフローでも引き継げる**という便利な機能。

### 4. Tavily の HTTP Request をメインから移植する

1. メインの `デモ` キャンバスに戻り、**Tavily の HTTP Request ノードをコピー**（Cmd/Ctrl + C）。
2. サブエージェントのキャンバスに戻り、**Cmd/Ctrl + V** で貼り付け。
3. 貼り付けたノードを、**サブエージェントの AI Agent の「Tool」に接続**する。

→ これで **Tavily 検索だけを持った、検索特化型のAIエージェント**ができた。

> 【追記】⑦で API キーを **Credential に登録**していれば、ノードをコピーしても**キーはそのまま引き継がれ、貼り直す必要がない**。ヘッダーに直書きしていた場合との違いをここで体感させられる。

### 5. テスト用データをピン止めする

サブエージェントのトリガーは「他のワークフローから呼び出されることで起動」するため、**このワークフロー単体で実行しても、呼び出す親がいないのでテストできない。**

1. トリガーノードを開くと、画面右側に **Output** の欄が出る。
2. 右上の**鉛筆マーク（Edit Output）**からデータを直接書ける。
3. 例として **`1`** を出力する JSON を書く。
4. 保存すると**ピン止め**される（**ピンのアイコンがオレンジ色**になる）。

→ テスト実行時は**常に同じデータが流れてくる**状態になる。

### 6. AI Agent のプロンプト設定

1. AI Agent ノードを開くと、左側の Input にピン止めしたデータ（`query: 1`）が表示されている。
2. パラメータ **Prompt** を **`Define below`** に切り替える。
   > 動画で「Source for Prompt (User Message) を下の選択肢に」と言っているのがこれ。**現行のパラメータ名は `Prompt`、選択肢は `Take from previous node automatically` / `Define below`。**
3. 現れた **Prompt (User Message)** の欄に、Input から **`query`** をドラッグして式として載せる。
4. AI Agent を実行して、エラーが出ず**緑色**になれば正解。

### 7. サブエージェントのシステムメッセージ

**Add Option → System Message** から、役割を明示する。例：

> あなたは優秀なリサーチャーです。ユーザーから受け取ったメッセージの内容を、あなたが持っている HTTP リクエストのツールを使ってリサーチをして、その結果だけを回答してください。

→ **サブエージェントの役割はしっかりと明確に指示する。**（保存操作は不要）

### 8. メインエージェントと接続する

1. メインエージェントのワークフローに戻る。
2. サブエージェントに移した **HTTP Request ノードをメインから削除**する。
3. メインの AI Agent の Tool に **`Call n8n Workflow Tool`** を追加する。
4. ノードを開き、**Source** を `Database` にして、**先ほど作成したサブエージェントのワークフローを選択**する。
5. **Description** に、このツールをいつ使うべきかを書く（エージェントはこの説明を読んで呼ぶか決める）。

→ これでこのツールは**「サブエージェントサーチという部下を呼び出すツール」**になった。

### 9. メインエージェントのシステムメッセージを修正

新しく入った部下（サブエージェントツール）のことを教える。例：

> あなたに「サブエージェントサーチ」というリサーチが得意な部下がいます。ユーザーから何かしら調べてほしいと依頼された場合、必ずこのサブエージェントサーチツールを使ってリサーチを実行してください。

### 10. サブエージェント側の修正（ピンを外す）

- サブエージェントのトリガーに設定した**テスト用データのピンを外す**。
- ピンを外したままだと、**メインから何を渡しても常に同じデータで動いてしまう**。忘れやすいので必ず確認する。

### 11. 【新規追加】本番で動かすなら、サブワークフローを Publish する

> ⚠️ **動画にはない、現行 n8n で必須の手順。**
>
> `Call n8n Workflow Tool` の Source を `Database`（＝一覧から選ぶ方式）にしている場合、
>
> - **キャンバスのチャット欄からのテスト実行では、Publish しなくても動く。**
> - **本番実行では、呼び出されるサブワークフローが Publish されていないと失敗する。**
>   - エラー：`Workflow is not active and cannot be executed`
>   - しかもこのエラーは**ツールの実行結果としてエージェントに返される**ため、長いエージェントの返答の中に埋もれて気づきにくい。
> - **症状**：「エージェントが『データを取得できませんでした』と言う」
> - **確認すること**：①サブワークフローが Publish 済みか ②サブワークフローの実行履歴に実行記録が残っているか

講座では、⑧の時点で**サブエージェント側を Publish させておく**とよい。受講者が後で自分のワークフローを本番稼働させたときに、この落とし穴を踏まなくて済む。

### 12. 動作確認

1. メインエージェントのチャット欄に **`織田信長について調べて教えてください`** と送信。
2. → 「織田信長は日本の戦国時代の〜」という回答が返ってくる。

**動作の流れ**：メインエージェント自体にはリサーチ用ノードがないが、`Call n8n Workflow Tool`（サブエージェントサーチ）が別のワークフローを呼び出す → サブエージェント側でリサーチ → 結果をメインが受け取る → メインの Chat Model が判断して出力する。

## 【追記】同一キャンバスで組む場合（AI Agent Tool）

受講者が「別キャンバスは面倒」と感じたとき用の代替手順。**5分で紹介できる。**

1. メインの AI Agent の **Tool** に **`AI Agent Tool`** を追加する。
2. パラメータを設定する。

   | パラメータ | 内容 |
   |---|---|
   | **Description** | 親エージェントがこのサブエージェントに何を任せるべきかの説明。**ここが具体的なほど正しく委譲される** |
   | **Prompt (User Message)** | このサブエージェントに何をさせ、何を返させるか |
   | **System Message**（Options） | サブエージェントの役割・制約 |

3. この AI Agent Tool に、**Chat Model とツール（例：HTTP Request Tool）を接続**する。
4. **入れ子にして多段構成にもできる。**

違いのまとめ：

| | AI Agent Tool（同一キャンバス） | Call n8n Workflow Tool（別キャンバス） |
|---|---|---|
| 作る手間 | 少ない | 多い（別ワークフロー＋トリガー＋入出力の設計） |
| データ受け渡し | 意識しなくてよい | Input data mode / Workflow Inputs の設計が要る |
| 再利用 | そのワークフローの中だけ | **複数のワークフローから使える** |
| 本番での Publish | 不要（親のワークフローを公開すればよい） | **サブワークフローも Publish が必要** |
| 保守の分離 | キャンバスが大きくなる | **完全に分離できる** |

## 動画中の入力例・設定値（現行版）

| 項目 | 値 |
|---|---|
| サブエージェントのトリガー | `Execute Sub-workflow Trigger`（When Executed by Another Workflow）／Input data mode: **`Accept all data`** |
| サブエージェントの Chat Model | OpenRouter Chat Model（既存 Credential を再利用） |
| サブエージェントのツール | HTTP Request（Tavily／メインからコピー） |

## 講師が強調すべき点（現行版）

- **一人のエージェントに詰め込みすぎない。役割ごとに分ける。** これはツールが増えやすくなった現行ではより重要。
- **分け方は2通りある。**「再利用するか／保守を分けたいか」で **AI Agent Tool** と **Call n8n Workflow Tool** を選ぶ。
- Credential は**一度登録すれば別ワークフローでも引き継げる**。
- サブエージェント単体ではテスト実行できないため、**ピン止めしたテストデータ**を使う。**テストが終わったら必ずピンを外す。**
- **本番では、呼ばれる側のワークフローも Publish されていなければならない。**
- 既に同一キャンバスに作ってしまっていても心配不要。**ノード群をコピーして別ワークフローに引っ越せば**、メインから呼び出せる。

## 【発展】n8n の Agent Builder（Preview）

現行の n8n には、**ワークフローとは別に「エージェント」を第一級の成果物として作る機能**が追加されている（Preview、n8n Cloud および一部のセルフホスト）。

- **構成要素**：モデル／Instructions（システムプロンプト）／ツール／Web 検索／スキル／チャンネル（Slack・Telegram など）／スケジュール／**サブエージェント**／ナレッジベース／メモリ
- **ドラフトと公開バージョン**があり、ワークフローと同じく「編集は自動保存、公開はスナップショット」という考え方で動く。
- **サブエージェントは「公開済みの別エージェント」として登録する。**

講座では**深入りせず、「この先こういう作り方もある」と示すにとどめる**のが適切。Preview 機能であり、挙動が変わる可能性があるため。
